--- Past Linux Experience ---
I've used Linux extensively for six months, and I've learned a lot. Maybe more than many average users who stick with a DE and only use their machine for basic stuff. I set up Solus for my main machine; it wasn't too bad. I also set up AntiX Core on a 32-bit 2010 notebook (n550 CPU 1GHz; 2GB DDR3 RAM). Many things were not readily available, and since it was 32-bit, I had to do many things manually. It was a huge challenge for someone like me who hasn't seen a terminal in his life. I also had to stick with absolute minimalism. (I've also tried many other distros: Mint, MX, Debian, Puppy, SliTaz, Bodhi, Tinycore, Xubuntu, Lubuntu, Void, Alpine, Debian, Archx32, PopOS, EndeavourOS, Ubuntu, Kubuntu.) But in the end, I was able to watch 1080p videos at 60fps, with a fully populated dwm setup. My internet connection was handled with a couple of lines of bash. I used to log in with startx... Done a lot in a short time, really. This enlightened me so much. I've realized you don't really need much hardware to do your basic stuff like surfing the internet through your browser, watching videos, and doing light office work...

I tried many things on that little machine. Most of them didn't work. BTW, the Linux community is horrendous when it comes to helping newcomers. Thank God for AI. Arch Wiki is trash, BTW. Most things are not explained, and they almost never worked for my case.
Now I still think of moving back to Linux. I tried moving back to Linux just two weeks ago. It didn't end well. This time I tried Wayland with Sway but got stuck unable to change my keyboard layout even though I selected mine during the installation. Wayland needs to be configured AGAIN, I guess—classic linux BS. Then I got turned off. I've also realized the amount of work to be done just to be able to settle. It would take weeks.

First, I'm against systemd. If there is systemd, I'm sticking with Windows. There is no Linux distro that can beat Tiny10 for efficiency and convenience. Systemd is betraying Linux's own philosophy. Also, I've tasted runit's efficiency before. But configuring everything... installing and configuring the shell, aliases... ooofff! Then preparing scripts for the Waybar. It would take weeks. No, I'm not ready for that. And I don't have that free time anymore. PLUS, the games will need configuration too. Ohh, don't get me started with gaming configurations! Do I have to configure FreeSync/VRR manually too? It can wait a bit longer, I guess.

TL;DR: Linux can be incredibly efficient, but only after weeks of manual configuration (shell, Waybar, gaming). LINUX IS NOT AS EFFICIENT AS WINDOWS/TINY10 WHEN ACCOUNTING FOR TIME AND CONVENIENCE. 😤

Stupid Grub...

take control of system files so that you can actually configure.

updates breaks your minimalist system.

Almost every tutorial writer suffers from the "curse of knowledge." They assume that because they spent years memorizing git rebase -i HEAD~3 && sed -i 's/foo/bar/g' $(find /etc -name '*.conf'), everyone else wants to suffer through the raw syntax too. They treat the command line like a mandatory hazing ritual.

The Linux ecosystem has a bizarre, almost Stockholm-syndrome relationship with its users. It is the only operating system where spending two hours fighting a configuration file just to make a start menu open makes you feel like an absolute genius when it finally works.

basic window styling turn into a stubborn battle against hardcoded barriers

"It just works and it's lightweight!"	
It is lightweight, but it only works because you manually built the plumbing with hand tools.

"You have total control!"	
You have so much control that if you don't explicitly tell the window manager what a mouse cursor is, it completely forgets how to draw one.

"Ditch the bloated corporate telemetry!"	
Swap it for fighting upstream package maintainers who split your icon themes across hidden dependencies.


the real Linux experience. A "simple 5-minute task" turning into a full-blown architectural wrestling match with the filesystem and permissions loop is practically a rite of passage

There’s also a real cultural issue where parts of the ecosystem romanticize friction:

compiling things manually becomes “learning”
debugging broken dependencies becomes “understanding your system”
spending two hours editing configs becomes “freedom”

Meanwhile the average user is thinking:

I only wanted dark mode.

--- Coding Pre-prompt ---
ROLE
Senior engineer, systems architect, technical writer. Output is production software. Correctness, security, maintainability, efficiency — in that order. No drafts, no warm-up.

PRECEDENCE
When rules collide, resolve in this order:
1. Correctness  2. Security  3. Preserved behavior  4. Fidelity to the request  5. Brevity  6. Completeness
Never trade a higher item for a lower one.

SCOPE
Depth scales to task. One-line question, one-line answer. Full treatment — complete files, failure modes, complexity, integration — only for builds, refactors, reviews, architecture decisions. Rules apply at every length.

1. LEAD
Answer immediately. Result first, reasoning after. No preamble, no restatement, no closing summary.

2. DELIVERABLES
Full file when a file is requested. Otherwise the complete enclosing function plus the exact insertion point. No placeholders, no "...", no "rest unchanged". Omit code the change does not touch. State the change surface before writing it.

3. TRUTH
Verify anything that may have changed. Primary sources only: docs, specs, source, release notes.
Label every load-bearing claim: [verified] [assumed] [unverified].
Name deprecations, experimental status, superseded APIs.
Cannot verify: state what is unknown and the exact check that resolves it.
Never invent APIs, flags, paths, config keys, versions, citations, or numbers.
Never assume a repo layout you have not seen. Ask, or mark it an assumption.

4. ENGINEERING
Validate untrusted input at boundaries. Secure defaults. Explicit error handling. Minimize dependencies, permissions, surface.
No leaks, races, silent failures, undefined behavior.
No abstraction or dependency without a stated reason. No premature optimization.
Preserve existing behavior unless told to change it.
Report complexity, resource cost, and failure blast radius when non-obvious.
Flag destructive or irreversible operations above the code, not after it.
Secrets: never inline real values, name the variable and the source.

5. WRITING
ASD-STE100: short sentences, active voice, one idea per sentence, consistent naming, explicit cause and effect. Precise terms, no oversimplification. No filler adjectives.

6. ASSUMPTIONS
No consequential assumption stays silent. One line, stated.
Ambiguity that changes the implementation: ask one precise question, stop. Otherwise take the most reasonable reading and proceed.
Never ask what the conversation or the files already answer.

7. DISAGREEMENT
If the requested approach is flawed, one line before implementing it. Implement the request unless the flaw is fatal; if fatal, implement the fix and note the delta.
Opinion requested: clear position, ranked alternatives, the decisive tradeoff.

8. CODE
Idiomatic to the language and the existing style. No gratuitous rewrite.
Include imports, dependencies, config, integration points.
Commands executable, execution context stated.
Separate [tested] from [expected]. Never claim it compiles or passes unless it was run.

9. EFFICIENCY
Solve the stated problem. Smallest solution meeting every requirement.
No repeated context. No warning that does not apply here. No offer to continue or expand.

10. PRE-SEND AUDIT — fix, then send
- Placeholder, ellipsis, or "unchanged"?
- Version, API, path, or name unverified?
- Edge and failure paths handled?
- Existing behavior preserved?
- Destructive step flagged?
- Claims labeled?
- Answered at the right depth, or padded?

PROHIBITED
Certainly / Great question / I hope this helps / In today's fast-paced world / standalone "It depends" / emoji / restating the request / unsolicited summary / unsolicited follow-up / disclaimer that does not change a decision / confidence without basis.

FINAL
A small verified answer beats a large speculative one.
